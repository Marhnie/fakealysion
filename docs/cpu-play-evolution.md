# CPU 자가대전 진화 로그 (전문가 레벨)

목표: CPU가 스스로 자가대전(self-play)으로 판단 파라미터를 최적화해서 더 강해지게 한다. 학습은 전부 **오프라인 Node**에서 하고, 결과는 작은 정적 파일 `data/cpu-params.json`(약 1KB)로만 배포한다. 브라우저는 서버·학습 없이 이 파일을 읽기만 하며, 파일이 없거나 깨져 있으면 내장 기본값으로 안전하게 폴백한다.

## 1. 측정 장비 (rig)

| 파일 | 역할 |
|---|---|
| `scripts/cpu-arena.mjs` | 두 CPU 설정(A, B)을 고정 덱 풀에서 N판 대전. **양쪽 선후공 모두**(쌍 단위), 같은 덱·같은 난수 시드(공통 난수), 자식 프로세스 병렬. 승률 + Wilson 95% 신뢰구간, 평균 턴 수, 결정당 시간(평균/최대) 출력. `--timing N`은 벽시계 예산(브라우저와 동일)으로 실제 결정 시간 표를 측정 |
| `scripts/arena-core.mjs` | 한 프로세스 안의 게임 실행기 + 결정적 덱 풀 + 설정 명세(`{level, search, params}`) 해석 |
| `scripts/arena-pool.mjs` | 상주 자식 프로세스 풀(동적 분배). 한 게임이 90초 넘게 멈추면 그 워커를 죽이고 새로 띄운 뒤 그 쌍을 오류로 센다 |
| `scripts/arena-worker.mjs` | 자식 프로세스 본체 |
| `scripts/cpu-evolve.mjs` | 오프라인 최적화기(sep-CMA-ES). 아래 3절 |

덱 풀(시드 고정, 항상 동일): 스타터 기반 8종 + 색 일관 합법 덱 16종 = 24종. 앞 16종이 **학습용(train)**, 나머지 8종이 **검증용(val, 학습에 절대 미사용)**. 모든 덱은 `S.deckLegality` 통과.

명세 예시: `easy` / `normal` / `hardH`(어려움 휴리스틱, 탐색 없음) / `hard`(= UI 어려움: 탐색 켜짐) / `expert` / `@파일.json` / `'{"level":"hard","params":{"hardThrA":-1}}'`.
탐색 예산은 헤드리스에서 **노드 수**로 준다(기계 무관, 결정적): hard = 36노드/깊이 4/샘플 2, expert = 60노드/깊이 4/샘플 2.

```
node scripts/cpu-arena.mjs --a expert --b hard --games 300 --seed 5 --pool all --workers 11 < /dev/null
node scripts/cpu-arena.mjs --a expert --timing 80 < /dev/null      # 실제 벽시계 결정 시간
```

## 2. 파라미터(명시적·주입 가능)

`src/cpu.js`의 `TUNE` 객체가 곧 파라미터 벡터이며, 플레이어별 재정의는 `cfg.params`로 들어간다(`makeParams(부분)`). **기본값은 이전 동작과 정확히 동일**하다(쉬움/보통/어려움은 `params` 없이 그대로 동작). 튜닝 범위는 `PARAM_RANGES`.

키워드 값(블로커/재밍/관통 등)과 옵션·테이머 가치는 `stackValue`/`optionValue` 안의 상수라 이번에는 벡터에 넣지 않았다(한계 6절).
`cpusearch.js`는 `cfg.params`를 받아 평가·탐색 규칙에 반영하고(`evaluate(state,p,P)`, `weightsFor(P)`), 탐색 안의 "상대 정책"은 항상 기본 어려움(현실적인 상대 모델)이다.

## 3. 최적화 (sep-CMA-ES)

`scripts/cpu-evolve.mjs`: 대각 공분산 CMA-ES(CSA 스텝 크기), 후보는 정규화 [0,1]^d로 표현. 한 세대의 모든 후보가 **같은 시드·같은 덱·양쪽 선후공**으로 겨루는 공통 난수. 적합도 = 0.5 x 기본 어려움(기본 파라미터) 상대 승률 + 0.3 x 명예의 전당(최근 4세대 최고 후보 중 1명) 상대 승률 + 0.2 x 보통 상대 승률(첫 세대는 0.5/0.5). 마지막에 최근 최고 후보 + 평균벡터를 **새 시드 + 더 큰 N**으로 재평가(finalists)하고, 승자를 **검증 덱 풀**에서 다시 확인한다.

### 3.2 추가 실험 — 채택하지 않음
- 첫 시도(인구 16, 세대당 20쌍)는 중간에 재시작(중복 실행 정리) — 결과 미사용.
- 채택 벡터에서 이어 돌린 2차 진화(인구 24, 60쌍, sigma 0.12, 12세대, 20분): finalists 0.509~0.535 [학습], 검증 0.525. 1차 벡터보다 낫다는 근거가 없어 **채택하지 않음**(노이즈 한계).

## 4. 어려움 vs 전문가 — 무엇이 다른가

| | 어려움 | 전문가 |
|---|---|---|
| 판단 구조 | 휴리스틱 + 탐색 | 동일 |
| 파라미터 | 기본값 | `data/cpu-params.json` (정책 19개 튜닝값) |
| 탐색 시간 예산(브라우저) | 소프트 0.9초 / 하드 캡 2.5초 | **소프트 1.25초 / 하드 캡 1.4초** (폰 기준 최악 ≈1.5초 이내) |
| 헤드리스 노드 예산 | 36 | 60 |

UI: `Cpu.LEVEL_LABEL.expert = '전문가'`를 `renderSetup`이 그대로 순회하므로 시작 화면에 자동으로 뜬다(브라우저에서 확인: 쉬움/보통/어려움/전문가, 전문가로 대전 시작해 CPU가 정상 진행, 콘솔 오류 0). `4수 읽기` 체크박스도 전문가에 표시된다. `data/cpu-params.json` 로드는 `main.js init()`에서 `Cpu.loadParams()`(try/catch, 실패 시 내장 기본값)로 한다.
쉬움/보통/어려움 코드 경로는 `params`가 없으면 이전과 동일하다(기본 TUNE 값 그대로).

## 6. 결정 시간 표 (벽시계, 단일 프로세스·비경쟁, 이 PC)

| 레벨 | 결정 수 | 중앙값 | p95 | p99 | 최대 | 평균 깊이 | 평균 노드 |
|---|---|---|---|---|---|---|---|
| 쉬움 / 보통 | (전 게임) | 약 2 ms | - | - | 약 0.2 s | - | - |
| 어려움 휴리스틱만(hardH) | (전 게임) | 약 5 ms | - | - | 약 0.2 s | - | - |
| 어려움(탐색 0.9초/캡 2.5초) | 90 | 488 ms | 1138 ms | 1444 ms | 1444 ms | 1.82 | 55 |
| 전문가(탐색 1.25초/캡 1.4초) | 84 | 698 ms | 1415 ms | 1432 ms | 1432 ms | 2.04 | 62 |

전문가의 하드 캡 1.4초는 노드 하나의 시뮬레이션이 끝난 뒤에야 확인되므로 최대값이 캡을 최대 수십 ms 넘는다(측정 최대 1.43초). 병렬 부하가 있는 상태의 측정(예: `test-cpu-search.mjs` p95 1578 ms)은 더 느리게 나온다. 폰은 이 PC보다 느리므로 같은 캡에서 더 얕게 읽는다(캡이 시간 상한을 보장).

노드당 비용이 약 15~30 ms로 큰 이유는 프로파일상 규칙 엔진의 훅 조회(`activeHooks`, `isAsDigimon`, `restoreState` 등 `state.js`/`snapshot.js`)이며 CPU 코드가 아니다. 그래서 "4수 읽기"는 실측 평균 깊이가 1.5~2에 그친다(대부분 후보 행동 1수 + 롤아웃 평가).

## 7. 정보 은닉·안전 감사

- 감사: `cpu.js`/`cpueval.js`/`cpusearch.js`의 상대 숨김 영역(패/덱/시큐리티) 접근은 모두 `.length`(공개 정보: 장수)뿐이다. 탐색은 `determinize()`로 상대 패·시큐리티를 "보이지 않는 카드 다중집합"에서 표본추출한다.
- `scripts/test-cpu-search.mjs 60`: 결정성 60/60, no-peek(숨김 영역을 섞어도 결정이 안 바뀜) 40/40, 라이브 상태 불변·연속성 22/22, ALL OK.
- 회귀: `check-syntax` OK, `soak 60` 오류 0, `test-cpu` OK(정체/오류 0), `audit-effects`는 다른 작업자의 카드 추가 중에 99.9%(미커버 11)로 나오는 순간이 있었으나 전체 스위트 실행 시에는 100%였고 내 변경(CPU 코드)과 무관. `test-all`은 병렬 학습이 돌던 중 `test-cpu-search`만 600초 타임아웃으로 실패했고 단독 재실행은 통과(ALL OK).
- `cpu-hunt` 전문가 대 전문가 총 **1,148판**(mix 모드, 시드 4242/5151): 예외 0, 로직 정체 0. 60초 벽시계 캡(병렬 부하로 탐색 게임이 느림)에 걸린 3판은 턴 13~15의 정상 진행 중이었고, 캡을 늘려 재생하면 종료됨. `CONS OWNER` 3건은 기존 헌트 리포트에 있는 알려진 "남은 것"(BT7-083 등 소유자 이동)이며 레벨과 무관, `REJECT`(효과 없는 【메인】)도 기존 종류.

## 8. 한계와 다음 단계

1. 탐색 평가 파라미터(`evSec…deckLowW`)는 **튜닝하지 못했다**. 탐색이 켜진 게임은 게임당 수십 초라 시간 제한 안에서 적합도 평가를 충분히 못 돌린다(30분 x 11코어 = 게임 수백 판). 규칙 엔진 훅 조회를 빠르게 만들면(노드당 비용) 가장 큰 개선 여지가 있다.
2. 정책 파라미터의 이득은 작다(+3~7%p), 검증(미학습) 덱에서는 +3%p 수준으로 경계선. 적합도 노이즈(세대당 80판, 표준오차 0.055)가 신호와 비슷해 CMA-ES가 안정적으로 수렴하지 못했다(sigma가 0.17→0.25까지 커졌다가 0.19). 판수를 크게 늘리면(수십만 판) 더 나아질 수 있다.
3. 키워드 값·옵션/테이머 가치·카드별 휴리스틱은 코드 상수이며 벡터에 없다.
4. 사다리의 전문가 우위는 노드 예산 1.67배와 파라미터가 섞인 값이다(5절 주의). 벽시계 예산 그대로의 대전은 병렬 부하 때문에 신뢰하기 어려워 하지 않았다.
5. 탐색 안의 상대 모델은 기본 어려움 정책(파라미터 미주입)이다.
6. 덱 풀은 스타터 + 무작위 색 일관 덱이라 실제 메타 덱 분포와 다르다.

재현: `node scripts/cpu-evolve.mjs --keys policy --search none --pop 24 --pairs 40 --gens 60 --minutes 22 --finalPairs 300 --seed 21 --workers 11 --out run.json < /dev/null` (결과 JSON의 `best.params`를 `data/cpu-params.json`의 `params`에 넣는다).
