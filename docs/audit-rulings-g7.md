## 2. 발견하고 수정한 버그

### 2-1. `S.cardMentions` (src/state.js) — "「X」가 기술되어 있는" 판정에 특징(types) 배열 누락

- **증상**: 공식 일반 Q&A(제 룰링 파일 중 66개 카드에 동일하게 첨부된 "기재가 있는 카드" 질문)에 따르면 "「X」가 기술되어 있는 카드"는 **명칭·특징·효과·진화원효과·〈룰〉·진화조건·조그레스·데지크로스조건·버스트진화·업합체·링크·어셈블리조건**을 모두 스캔해야 함. 그런데 기존 `cardMentions`는 카드명과 `effectKo`/`inheritedKo` 텍스트에 `「X」`가 **문자 그대로 인쇄**되어 있는지만 확인했고, 카드의 `types`(특징) 배열 자체는 전혀 확인하지 않았음.
- **재현**: `EX13-037` 듀나스몬의 진화 조건·어셈블리 조건이 둘 다 `「윗체르니」가 기술되어 있는 Lv.5`. `BT18-039` 미스티몬은 `types: ["마법전사형", "윗체르니"]`로 특징에만 "윗체르니"를 갖고 있고 카드 텍스트 어디에도 "윗체르니"라는 글자가 없음(이름에도 없음). 수정 전에는 `cardMentions('BT18-039', '윗체르니')`가 `false`를 반환해 이 카드가 EX13-037의 진화 재료/어셈블리 재료로 인정되지 않았음(같은 문제로 EX7-019, EX7-023, EX8-074, EX10-041 등 다른 세트 카드도 영향을 받음. `evoTargetPredicate`/`parseJogressSide`가 전부 `cardMentions`를 재사용하므로 조그레스·일반 진화·어셈블리·링크 조건에 동일하게 영향).
- **수정**: `cardMentions`에 `(c.types || []).includes(n)` 분기 추가.
- **회귀 테스트**: `scripts/qa/qa-audit-g7-mentions.mjs` (3개 시나리오, 통과) — types 전용 매치, 기존 매치 방식 유지, `evoTargetPredicate`를 통한 실제 진화 조건 매칭까지 확인.

### 2-2. `src/cards/shard8.js` `OPS.s8_playOrUse` / `OPS.s8_evolve` — "코스트를 지불하지 않고 등장/진화"가 코스트 락을 무시함

- **증상**: 공식 Q&A(제 룰링 파일 9개 카드에 첨부): `ST12-03`류 "지불하는 등장 코스트를 마이너스할 수 없다" 카드가 있을 때 "코스트를 지불하지 않고 등장시킬 수 있다" 효과를 발휘하면 — **효과 자체는 발휘되어 카드가 등장은 하지만, 코스트는 마이너스되지 않는다**(= 원래 코스트를 그대로 지불해야 함). 진화 버전(`BT5-021`류 "지불하는 진화 코스트를 마이너스할 수 없다")도 동일.
- 실제 코드에서는 `free: true`일 때 `S.isPlayCostLocked`/`S.isEvoCostLocked`를 아예 확인하지 않고 무조건 코스트 0으로 처리하고 있었음. `EX12-013/027/041/043/050`, `BT26-012`(이 6장은 이미 `delta: -2` 방식이라 원래도 정상이었음)과 달리, `BT26-054`/`BT26-049`/`BT26-077`/`EX13-045`(손패에서 등장하는 분기)는 `free: true`를 쓰고 있어 실제로 이 버그의 영향을 받음. 진화 쪽은 `BT26-099`가 `s8_evolve`에 `free: true`를 사용해 영향을 받음.
- **수정**: 두 OPS 모두 `wantsFree = i.free && !locked` 형태로 바꿔, 락이 걸려 있으면 원래 코스트(및 기존 델타/자체 할인 로직)를 그대로 지불하도록 변경. 락이 없을 때의 동작(완전 무료)은 그대로 유지.
- **회귀 테스트**: `scripts/qa/qa-audit-g7-costlock.mjs` (3개 시나리오, 통과) — `BT26-054`가 `ST12-03` 존재 시 카드는 등장하되 코스트 4를 그대로 지불하는지, 락이 없을 때는 여전히 무료인지, `s8_evolve`도 동일 패턴인지 각각 확인(`OPS.s8_evolve`는 `BT26-099`가 《딜레이》 래퍼를 함께 쓰고 있어 실제 사용 경로 대신 OPS를 직접 호출해 격리 테스트).

### 2-3. `src/effects.js` `parseConditionText` — "상대의 메모리가 N 이상/이하(이)라면" 패턴 누락 → EX13-060 알파몬의 조건절이 통째로 사라짐

- **증상**: `EX13-060` 알파몬 【진화 시】 "…DP -8000. **그 후, 상대의 메모리가 5 이상이라면, 메모리 +2.**"에서 뒤 문장의 조건이 전혀 인식되지 않음. 기존 파서는 `(자신의)?메모리가 N…` (자신 쪽, 상대측 명시 없음)과 `메모리가 상대 쪽의 N 이상…`(어순이 다름, "메모리가"가 먼저 옴)만 처리했고, 실제 카드 텍스트처럼 **"상대의"가 "메모리가"보다 앞에 오는 어순**은 매치되지 않았음. 이 경우 "…한다. 그 후, <조건>라면, <효과>" 컴파일 경로(`effects.js` 4049~4058행)가 `test`를 못 구하면 `if (!test) return prefix;`로 **뒤 절 전체를 조용히 버림** — 즉 이 버그는 "항상 발동"이 아니라 **"상대 메모리와 무관하게 절대 발동하지 않음"**이었음(메모리 +2가 완전히 죽어있던 효과).
- 같은 어순(`상대의 메모리가 N…`)을 쓰는 카드는 전체 DB에서 `BT25-019`, `BT26-078`, `EX13-060` 3장뿐. `BT25-019`는 이미 전용 스크립트(`shard7.js`)로 직접 `oppMemory()`를 써서 정상 동작 중이었고, `BT26-078`도 이미 전용 스크립트(`shard46.js`, `memOf(state, opp(...)) < 5`)로 정상 동작 중이었음. **`EX13-060`만 전용 스크립트가 없어 제네릭 컴파일러에 전적으로 의존**하고 있었고, 이 카드가 이번 버그의 실질적 피해자.
- **수정**: `parseConditionText`에 `^상대의\s*메모리가\s*(-?\d+)\s*(이하|이상)(?:이)?라면$` 분기 추가, `-mem(ctx)`(상대 부호) 기준으로 비교.
- **회귀 테스트**: `scripts/qa/qa-audit-g7-oppmemory.mjs` (3개 시나리오, 통과) — 실제 EX13-060 진화 세그먼트를 `drain()`으로 돌려 상대 메모리 5 이상/미만 두 경우 모두 확인, 컴파일된 조건 함수 자체도 단위 확인.

## 3. 의심되나 해결하지 못한 것 (설계상 이유로 이번 패스에서 수정 보류)

### ≪관통≫(Piercing) 필수 시큐리티 체크가 "배틀할 수 있다" 스크립트 효과에서 아예 발동하지 않음

- 공식 Q&A(EX12-052 15개, EX13-045 13개, EX13-076 11개 등 다수)에 명시: 관통을 가진 자신의 디지몬이 어택 중, 카드 효과("이 디지몬과 상대의 디지몬 1마리로 배틀할 수 있다")로 상대를 배틀에서 소멸시키면 **관통이 유발·발휘되어야 함**(단, 한 번의 어택에서 관통 시큐리티 체크는 총 1회만).
- 코드 확인 결과 `S.resolveDigimonBattle`이 반환하는 `res.piercing` 플래그는 **정상 어택 흐름의 마지막 배틀**(main.js 약 2968행, cpusim.js 약 166행)에서만 소비됨. 카드 스크립트가 직접 `S.resolveDigimonBattle`을 호출하는 모든 경로 — 제네릭 컴파일러의 `n5_battle`/`OPS.s8_battle`(shard8.js), `EX12-052`(shard42.js), `EX13-044`/`EX13-045`(shard130.js), `BT25-020`(shard7.js) 등 — 는 `res.piercing`을 전혀 확인하지 않아 **관통 체크가 조용히 누락됨**.
- 제가 담당한 세트에서 특히 잘 드러남: `EX13-045`, `EX12-052`, `EX13-076` 모두 인쇄된 키워드에 《관통》을 갖고 있고, 셋 다 정확히 이 "배틀할 수 있다" 패턴을 씀.
- **왜 이번에 고치지 않았는가**: 제대로 고치려면 (1) 카드 스크립트에서 "지금 시큐리티 체크를 강제로 1회 발동" 요청을 던질 수 있는 새 훅(기존 `ctx.startAttack`/`ctx.attack`/`ctx.endAttack` 패턴과 동일한 방식)을 추가하고, (2) 이를 main.js(대화형 UI), cpusim.js(헤드리스 CPU/soak 드라이버), 그리고 여러 QA 라이브러리(`scripts/qa/lib*.mjs`)의 `ctx`에 각각 구현해야 하며, (3) "한 어택당 관통 체크는 1회"를 어택 단위로 추적하는 상태(`state.attackCtx`)가 필요한데, 정작 `EX13-045` 같은 카드는 스크립트 안에서 `ctx.startAttack()`을 호출해도 그 호출이 지연 큐(setTimeout/effAtkQ)로 넘어가 스크립트가 도는 시점엔 아직 `state.attackCtx`가 비어 있음 — 즉 "이 배틀이 어느 어택에 속하는지"를 판단하는 기존 아키텍처 자체가 이 케이스를 다루도록 설계돼 있지 않음. main.js/cpusim.js/effects.js 세 파일을 넘나드는 설계 변경이 필요하고, 지금 이 감사와 동시에 다른 7개 에이전트가 정확히 이 공유 파일들을 동시에 건드리고 있어 충돌 위험이 매우 큼. 그래서 이번 패스에서는 정확한 재현과 원인만 문서화하고 수정은 보류함(후속 작업으로 분리 권장).

## 4. 시간 부족으로 건너뛴 것 (정직하게 밝힘)

- 371개의 고유 질문 텍스트는 전부 읽고 훑었지만, **코드까지 직접 추적/검증**한 것은 빈도(반복 첨부 횟수)와 리스크 키워드(동시유발, 타이밍, 진화원, 소멸/파기, 시큐리티, 코스트 등) 기준 상위 약 25개 일반 규칙 + 개별 카드 6장(EX13-045/EX12-052/EX13-076/EX12-047/EX13-060/EX13-064) 정도로 제한함. 나머지 n=1(카드 1장에만 첨부된) 저빈도 질문들, 특히 "예/아니오, 인쇄된 그대로입니다" 유형은 리스크가 낮다고 판단해 코드 대조 없이 넘어감.
- 구체적으로 검증하지 못한 항목:
  - `{트래시}`/`{시큐리티}` 스코프 한정 효과("그 카드가 트래시/표시 시큐리티에 있는 동안만 발휘 가능")의 일반 규칙 — 관련 카드(`BT26-078`/`BT26-079`/`BT26-082`/`BT26-100` 등) 각각의 전용 스크립트가 있는 것은 확인했지만, 일반 규칙 자체가 엔진에 올바르게 강제되는지는 개별 확인 못함.
  - "덱이 증가했을 때" 트리거(`BT26-001`/`BT26-015`/`BT26-060`, 덱이 줄었다 늘었다 해도 "증가" 판정이 되는지 등의 세부 사항) — 코드 추적 안 함.
  - "DP 소멸 효과의 상한 +N000"(`EX13-007`/`EX13-010`, 숫자가 적힌 소멸효과만 적용되고 "이 디지몬의 DP 이하" 같은 비고정 소멸효과엔 적용 안 됨) — 코드 추적 안 함.
  - `EX13-031` 스카몬 대왕의 "원래 명칭·색·DP로 변경" 이후 〈룰〉로 파생된 정보/효과로 얻은 정보/진화·퇴화 후 정보 유지 등 다층 규칙(엔트리 6개) — 로직이 복잡해 이번엔 코드 대조를 생략.
  - `EX12-034`/`EX12-064` 등에서 "동시에 여러 【서로의 턴】 효과가 있을 때 룰체크 끼어들기 순서"류의 매우 세밀한 순서 규정 — 기존 slice1~6 감사에서 이미 폭넓게 검증된 동시유발 처리 인프라를 신뢰하고 개별 재확인은 생략.
- 이미 확인해서 "정상"으로 판단한 것들(버그 아님, 참고용):
  - 카운터 효과 1회/어택 제한, 관통 시큐리티 체크 1회 제한, DP 0 즉시 소멸 안 함(룰체크 배치), "Lv.N 이상의, A 이거나 B" 양쪽 모두에 Lv 조건 적용, 시큐리티 체크 시 【시큐리티】 효과 우선 발휘 후 나머지는 턴 플레이어측부터, "-N:" 줄이 본문에 안 붙음(EX13용 기존 테스트로 확인), 테이머로부터 진화(`EX13-064` ← `EX13-074` 키시베 리에, `canEvolveAny`가 동적으로 올바르게 인식함을 실측 확인) 등은 모두 코드/실측으로 이미 정상 동작 확인함.
